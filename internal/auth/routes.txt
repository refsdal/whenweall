internal/auth verified route table — the frontend contract
=============================================================

Generated by actually probing a running test server (see the now-deleted
internal/auth/routedump_test.go — TestRouteDump — for the method used: every candidate route
below returned something other than 404 when hit with the listed method; a route not on this
list, or hit with a different method, 404s). Pinned Limen commit:
c6a34aa6dcb4d51a480e2c6ed9cb43e5c6f92ac4.

All routes are mounted under the base path /api/v1/auth (internal/auth.buildLimenConfig's
limen.WithHTTPBasePath). "protected" means the route 401s with no session cookie.

Limen's "CSRF protection" (on by default, middlewareCSRFProtection in limen/middlewares.go) is
not token-based — there is no CSRF token to fetch or echo back. It's a content-type/header check
run on every non-GET/HEAD/OPTIONS request, before the auth check: the request passes if its
Content-Type (ignoring any ";charset=..." suffix) is exactly "application/json" (or matches the
current route's configured AllowedContentTypes, when it has any), OR it carries a non-empty
Authorization or X-Requested-With header; otherwise it's rejected with 403 "Forbidden" — no
"code" field, unlike our own envelope. A same-origin fetch()/axios JSON POST satisfies this
trivially (it sets Content-Type: application/json); a plain HTML <form> POST or an <img>/<script>
cross-site request does not, and gets the 403 rather than ever reaching a route handler. So a
POST/PUT/PATCH/DELETE route below still requires a session even though probing it
unauthenticated with a JSON body shows 401 (not this 403) first. Our own CheckOrigin
(internal/httpserver/origin.go) is a second, independent check on top of this: an Origin-header
mismatch on a mutating /api/v1/* request 403s before either of Limen's own checks runs.

magic-link (/magic-link)
---------------------------
POST   /api/v1/auth/magic-link/signin                       public   (enqueues magic_link mail)
GET    /api/v1/auth/magic-link/verify                        public   (consumes the magic-link token)

magic-link/signin's JSON body accepts optional redirect_uri / new_user_redirect_uri /
error_redirect_uri fields (plugins/magic-link/handlers.go's validateRedirectURLs), each checked
against IsTrustedOrigin (our BaseURL, i.e. cfg.AppURL, plus any WithHTTPTrustedOrigins entries —
buildLimenConfig sets none) and 403ing "... is not trusted" if given but not trusted. When
magic-link/verify's stored state carries a redirect_uri (or, for a first-time signup,
new_user_redirect_uri), a successful verify 303-redirects the browser there with the session
cookie attached instead of responding at all; a failed verify redirects to error_redirect_uri (or
redirect_uri) with ?error=... appended if either was given. Without any redirect_uri on the
original signin request, verify has nothing to redirect to either way: success renders the normal
JSON session response in the browser (SessionResponse), and failure renders the normal JSON error
response — neither is a redirect. The SPA must supply redirect_uri itself if it wants the browser
to land back on a specific page after clicking the emailed link rather than seeing raw JSON.

/authorize does NOT redirect (no 302 to the provider): it responds 200 with JSON
{"url": "<provider's own authorization URL>"} (plugins/oauth/handlers.go's SignInWithOAuth) and
sets its state cookie on that same response. The SPA is expected to navigate the browser to
`url` itself. /authorize also accepts optional ?redirect_uri= and ?error_redirect_uri= query
params, each checked against IsTrustedOrigin exactly like magic-link's (see above) and 403ing if
given but not trusted; redirect_uri defaults to BaseURL (cfg.AppURL) when omitted rather than
being required. Both are threaded through the OAuth state and used the same way on /callback:
success redirects to redirect_uri with the session cookie attached, failure redirects to
error_redirect_uri (or redirect_uri) with ?error=... appended — /callback, unlike magic-link's
/verify, always has at least the BaseURL default to redirect to, so it never falls back to a bare
JSON response.
